# Team Development & GitHub Conventions

This document outlines the operational systems and workflows for Team 4. All developers (and AI agents) must follow these procedures to maintain a clean git history and ensure that individual contributions are clearly visible for grading.

---

## 1. The GitHub Issue System
Every task, bug fix, or feature must exist as an Issue in the GitHub repository before development begins.

### Creating an Issue
* **Title**: Use conventional prefixes: `feat: <desc>`, `fix: <desc>`, `docs: <desc>`, or `db: <desc>`.
* **Description**: Include a brief summary of *what* is being changed and a clear **Definition of Done (DoD)** checklist.
* **Metadata**: 
  * Assign the issue to the person responsible.
  * Link it to the **ContestDB Project Board**.
  * Add relevant labels (`database`, `backend`, `frontend`, `worker`).

---

## 2. Git Branching & Workflow
We follow a strict feature-branching model. **Direct pushes to `main` are disabled.**

### Naming Branches
Trace branches directly to their active issue number:
* For features: `feat/issue-<number>-<short-description>`
  * *Example:* `feat/issue-4-submission-schema`
* For bugs: `fix/issue-<number>-<short-description>`
  * *Example:* `fix/issue-12-queue-deadlock`

### Commit Message System
Use Conventional Commits. Include the issue number in the commit message:
* Format: `<type>(<scope>): <short summary> (#<issue_number>)`
* *Examples:*
  * `feat(db): create submissions table and jsonb payload (#4)`
  * `fix(worker): handle connection timeout in psycopg3 (#12)`

---

## 3. Pull Requests (PRs) & Board Automation
Pull Requests are the bridge between local development and the production codebase.

### Linking PRs to Issues (Critical for Automation)
To automatically move tasks on the Project Board, you **must** link the PR to the issue it resolves. In the PR description, write:
```markdown
Closes #<issue_number>
```
*Example: `Closes #4`*

### System Lifecycle & Automation:
1. **Issue Created**: Placed in `To Do` column on the Project Board.
2. **Branch Checked Out**: Developer shifts the card to `In Progress`.
3. **PR Opened**: GitHub detects the `Closes #X` reference and automatically moves the issue and PR card to `In Review`.
4. **PR Merged**: Once another team member reviews and approves, the PR is merged. GitHub automatically:
   * Closes the referenced issue.
   * Moves both the PR and issue card to `Done`.

---

## 4. Documentation & Changelog Conventions
To keep the team aligned on *what* changes are being made and *why*, we maintain a unified documentation standard:

### Changelog Maintenance
We maintain a file at `docs/changelog.md`. Every time you merge a PR or complete a significant milestone, append a entry under the active version:
* **Format**:
  ```markdown
  ## [YYYY-MM-DD] - Issue #<issue_number>
  * **Changed Files**: `path/to/file1.py`, `path/to/file2.sql`
  * **Summary**: Brief explanation of what was added or changed and why.
  * **Author**: Name of developer.
  ```

### AI Agent Walkthroughs
When working with AI agents, the agent will update a `walkthrough.md` file in its execution workspace (under its artifacts directory). Human team members should review this walkthrough file before reviewing or merging PRs generated by the AI.
